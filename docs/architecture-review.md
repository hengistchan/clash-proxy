# 配置工作台架构与体验改进

2026-11-07。审查范围覆盖配置工作台、API、导入与历史、加密存储、生产启动、配置资产和自动验收。

## 用户任务与界面

总览按“准备配置资源 → 检查与修复 → 交付设备”组织操作。配置检查紧邻下载状态，错误不再被关系树挤到页面末尾。检查结果支持按严重程度筛选与展开全部；可以直接打开具体资源的编辑器，DNS、规则终位、循环引用和高级区块也有对应入口。

下载区区分当前草稿与最近成功版本。链接轮换说明对已有设备的影响，操作完成直接采用服务端返回的新状态，状态无法确认时隐藏旧链接并提供重试。API细节收进可展开区域。

## 数据与状态边界

- 工作台只在快照成功读取后一起切换配置标识和资源；请求序号淘汰过期的初始化与快照响应。失败保留当前配置并给出重试入口。
- 未保存输入由统一注册器保护。导航、刷新、切换配置、关闭编辑器和浏览器退出都能识别草稿；确认放弃会真正还原字段。后台刷新不覆盖未保存输入，写入期间阻止离开。
- 规则排序、历史恢复和全局资源操作采用同步写锁，避免多次提交旧的资源顺序或旧配置闭包。
- YAML解析从资源仓库抽为独立模块。结构错误、重复名称、不可无损保存的值在事务写入前拒绝；语义错误仍可保存为草稿，继续提供最近成功的配置。
- 历史恢复使用历史凭据；“导入占位来源时保留当前来源”仅用于导入。诊断使用完整的编译快照，API继续返回脱敏资源。
- 节点与策略组的命名冲突按资源表分别检查；direct/global模式无需依赖MATCH即可编辑规则，rule模式保留终位保护，并允许修复缺失、停用、错位或重复的MATCH草稿。

## 生产部署边界

生产启动器固定从项目目录解析数据库、密钥和模板路径，默认数据位于项目 `data/`，不会随 `.next` 重建被清空。检测到旧 standalone 数据时停止并保留文件，恢复步骤见 [SERVICE.md](../SERVICE.md)。构建前后均检查数据安全，Next.js文件追踪排除运行时数据，避免把本机数据库带入部署产物。

## 验收与能力范围

`npm run check` 覆盖导入失败的资源/历史/成功版本原子性、凭据隔离、精确恢复、规则编辑、导航保护和真实启动子进程。`npm run build` 验证生产构建和数据排除；`npm run test:e2e` 启动隔离数据库上的真实生产服务，用浏览器操作认证、导入、编辑、修复、下载、设备链接和恢复，并注入网络故障与延迟。

浏览器验收覆盖管理器，不代表 Stash 设备上的节点可用性或实际业务分流验收。桌面和手机布局使用真实生产包检查；浏览器测试使用临时数据库，原有数据库不参与操作验收。

## 破坏性操作确认

删除资源和规则、轮换或撤销设备链接使用应用内确认对话框，不再依赖可能被浏览器或 WebView 抑制的原生 `window.confirm`。确认后请求始终携带当前快照的 `If-Match`；引用保护返回 409 时保留资源并显示具体引用。删除、链接轮换与撤销均有真实浏览器回归，覆盖主机、节点、策略组、规则集、规则和链接生命周期。

## 资源仓库模块边界

`lib/repository.ts` 只保留初始化状态、`recordRevision` 和组合根，公开 API 与行为保持不变。读取模型与共享校验位于 `repository-shared.ts`；引用收集与重命名传播位于 `resource-references.ts`；导入替换位于 `profile-content.ts`；资源写入按代理、规则集、Hosts、高级区块分别位于 `proxy-repository.ts`、`rule-provider-repository.ts`、`host-repository.ts`、`advanced-repository.ts`；Profile/设置/快照与导入/历史/恢复分别位于 `profile-repository.ts` 和 `revision-repository.ts`。模块沿用 `rule-repository.ts` 的依赖注入方式，避免循环依赖。

后续工程审计整改以 [工程审计整改记录](engineering-audit-remediation.md) 为准；旧版规则包已从仓库移除，历史Python与静态等价检查数字仅记录前一轮验收，不属于当前CI。
